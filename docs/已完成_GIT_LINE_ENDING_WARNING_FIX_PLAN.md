# Git Line Ending Warning Fix Plan

## 任务目标 / Goal

- 消除当前仓库在 `git add` 等操作时出现的 `LF will be replaced by CRLF` 警告。
- 为仓库建立明确、稳定、可维护的换行符策略，避免后续继续反复出现同类提示。
- 确保修复方式不会破坏现有源码、文档和构建测试流程。

## 技术策略 / Technical Approach

- 先检查仓库是否已经存在 `.gitattributes`、`.editorconfig` 或其他换行符约束配置。
- 检查当前仓库层和用户层 Git 配置，重点确认 `core.autocrlf` 与 `core.eol`。
- 若仓库缺少显式策略，则优先通过 `.gitattributes` 在仓库内声明统一规则，而不是依赖每台机器的全局 Git 配置。
- 优先采用“仓库文本文件统一按 LF 存储”的方式，因为它更利于跨平台协作、Go 工具链和文档一致性。
- 在策略落地后进行验证，确保警告不再出现；如需补充少量归一化操作，则仅对受影响文件执行安全处理。

## 执行步骤 / Execution Steps

1. 在仓库内检查 `.gitattributes`、`.editorconfig` 和相关现有约束文件。
2. 检查当前 Git 换行符配置，确认警告产生的直接原因。
3. 按最小改动原则实现仓库级换行符策略修复。
4. 重新执行能触发警告的 Git 操作进行验证。
5. 对照本计划复核；全部完成后，将本计划文件重命名为 `已完成_...`。

## 验收标准 / Acceptance Criteria

- 仓库已存在明确的、可解释的换行符策略定义。
- 再次执行相关 Git 操作时，不再出现当前这组 `LF/CRLF` 警告。
- 工作区没有引入与本任务无关的大面积内容变更。
- 修复结果已对照本计划完成自检。

## 风险与边界 / Risks And Boundaries

- 不直接依赖修改用户全局 Git 配置作为唯一修复手段，避免把仓库问题转移给本机环境。
- 若仓库中存在必须保留 CRLF 的特定文件类型，需要通过更细粒度规则处理，而不是一刀切误改。
- 若验证过程中发现已有文件实际依赖特殊换行符行为，将先停在最小安全修改范围内处理。
