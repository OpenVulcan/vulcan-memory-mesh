# VMM 后续记忆提炼与画像合并分析（非决案）

本文档是面向后续设计讨论的分析稿，不是最终实施方案。

目标是结合 VMM 当前架构与 `memory-lancedb-pro` 的处理模式，分析“每轮原始入库 + 达到阈值后批量提炼 + 摘要记忆 + 画像合并”这条未来链路的可选方向、可借鉴点与风险点。

## 1. 当前现状

### 1.1 已经具备的基础能力

- `POST /vmm/post-action` 可以接收当前轮对话并写入主线持久化流程。
- 原始轮次在进入长期存储前，会经过：
  1. 入口清洗
  2. `MessageNormalizer`
  3. `NoiseGate`
- `NoiseGate` 已支持：
  - 正则噪声控制
  - 语义原型向量判定
  - SQLite 启动缓存
- 代码中已经预留了但尚未正式接通的后续处理器：
  - `summarize_entry`
  - `merge_profile`

### 1.2 当前还没有真正接通的部分

- 没有“达到 N 轮后批量触发 LLM 提炼”的正式调度链路。
- 没有“摘要候选二次校验”模块。
- 没有“画像证据提取”与“画像头部更新”的正式主线。
- 没有“摘要记忆 SQL + 向量库双写并回指原文”的正式数据模型。

## 2. 未来目标（讨论稿）

未来希望形成以下链路：

1. 每轮对话先进入原始轮次库。
2. 达到一定轮次或阈值后，触发一次批量 LLM 提炼。
3. 提炼输入不是只包含本次待处理轮次，还会附带一小段历史摘要上下文。
4. 一次提炼输出至少两类结果：
   - 当前一轮或多轮的核心摘要
   - 是否存在稳定画像信息
5. 核心摘要与原文绑定存储：
   - 原文或标准化轮次保存在关系库
   - 摘要向量保存在向量库
   - 向量条目回指 SQL 中的记录 ID，便于追溯
6. 如果存在画像信息，再调用单独的画像合并流程，更新头部画像。

## 3. `memory-lancedb-pro` 中值得借鉴的地方

### 3.1 抽取前过滤、抽取后验证、回退路径分层

`memory-lancedb-pro` 的优势不在于“某一条规则”，而在于它把整个记忆抽取拆成了多层：

1. 抽取前噪声过滤
2. LLM 提取
3. 候选结果再验证
4. Fallback 路径

这一点非常值得 VMM 借鉴。

对 VMM 来说，最有价值的不是照抄它的实现细节，而是引入“多层判定”的理念：

- 写原始轮次前做一次 `NoiseGate`
- 批量送 LLM 前再做一次提炼预过滤
- LLM 输出摘要/画像候选后，再做一次候选质量校验

### 3.2 `extractMinMessages` 的思路

`memory-lancedb-pro` 会先判断消息数是否达到最小阈值，再决定是否触发 smart extraction。

这很适合 VMM 未来的批处理模式。建议未来至少考虑以下配置：

- `extraction.min_turns`
- `extraction.max_batch_turns`
- `extraction.max_batch_bytes`
- `extraction.history_max_items`
- `extraction.history_max_bytes`

这样可以避免每轮都调 LLM，同时把批处理上下文控制在稳定范围内。

### 3.3 短文本不要在 semantic 预过滤层直接判死刑

`memory-lancedb-pro` 对 embedding 噪声预过滤采用了长度分层：

- `<= 8` 字符：跳过 semantic noise check
- `9 ~ 300` 字符：执行 semantic noise check
- `> 300` 字符：跳过 semantic noise check

这个策略的本意是：

- 太短的文本语义信号不足，容易误杀
- 太长的文本通常不是纯模板噪声

这对 VMM 未来“提炼前语义预过滤”有参考意义。

但需要注意：

- 这更适合“提炼前预过滤”
- 不建议直接原样搬到当前最终入库的 `NoiseGate`

因为 VMM 当前的 `NoiseGate` 更靠近长期记忆准入门，后面没有 `memory-lancedb-pro` 那么长的抽取与候选再过滤链路。

### 3.4 候选结果必须再校验

`memory-lancedb-pro` 会对 LLM 生成的候选做二次校验，例如：

- 摘要过短直接丢弃
- 摘要本身像噪声则丢弃

这一点对 VMM 非常关键。

如果未来 VMM 的 LLM 输出：

- `summary`
- `profile_evidence`

那么两者都不应无条件落库，而应经过独立的候选校验器。

### 3.5 Profile 走聚合合并，而不是碎片平铺

`memory-lancedb-pro` 把 profile 当成一个持续更新的头部档案，而不是一条条分散记忆。

这一点非常适合 VMM 当前“头部画像注入”目标。

建议未来明确区分：

- 原始轮次库
- 摘要记忆库
- 画像头部库

其中：

- 摘要记忆适合多条存储、向量检索
- 画像适合聚合更新、直接注入

## 4. 对 VMM 的适配建议（候选）

### 4.1 保持“原始入库”和“LLM 提炼”彻底解耦

建议：

1. 每轮对话先写入原始轮次库
2. 后台异步选择未提炼批次
3. 批量调用 LLM 做摘要与画像候选提炼

不要把“原始轮次接收成功”和“LLM 提炼成功”绑定成一个同步事务。

这样能降低：

- 接口延迟
- LLM 波动对入口稳定性的影响
- 重试带来的重复写入风险

### 4.2 增加“提炼检查点”与“批次状态”

未来如果要避免重复提炼，建议增加至少三类记录：

- `chat_turns`
  - 保存标准化后的原始轮次
- `extraction_batches`
  - 保存某次提炼消费了哪些 turn
- `memory_entries`
  - 保存提炼产出的摘要记忆

否则很容易出现：

- 同一批 turn 被重复提炼
- 旧摘要又被当成新摘要写入
- 画像被同一证据重复合并

### 4.3 历史上下文不要无限叠加

你提出“在送 LLM 时附加前几轮提炼后的历史内容”，这个方向是合理的，但不能无限叠加。

建议未来输入 prompt 固定拆成三段：

1. 当前待提炼批次
2. 最近少量历史摘要
3. 当前画像头部摘要（如有）

不要把太多旧原文一起带进去，否则容易出现：

- 摘要的摘要继续被总结
- 旧结论污染新结论
- 重复记忆明显增加

### 4.4 摘要与画像应分成两条后处理链

建议未来 LLM 一次输出结构化 JSON，但后续分别处理：

- `summary` 候选
- `profile` 候选

原因是：

- 摘要更像可检索的记忆条目
- 画像更像聚合状态

因此：

- `summary` 更适合写 SQL + 向量库
- `profile` 更适合调 `merge_profile` 做头部合并

## 5. 建议未来补的模块

### 5.1 `BatchAssembler`

职责：

- 从原始轮次库取未提炼 turn
- 组装当前批次
- 限制轮次数和总字节数
- 附加有限历史摘要

### 5.2 `ExtractionOrchestrator`

职责：

- 判断是否达到提炼触发条件
- 调用 `summarize_entry`
- 解析结构化输出
- 决定是否继续写入摘要和画像流程

### 5.3 `SummaryCandidateValidator`

职责：

- 过滤无价值摘要

建议至少拦截：

- 过短摘要
- 模板化摘要
- 噪声型摘要
- 只有“用户问了一个问题”这种空洞总结

### 5.4 `ProfileCandidateValidator`

职责：

- 判断画像证据是否足够稳定、是否值得进入头部画像

建议重点防止：

- 临时任务性信息污染画像
- 会话级短期偏好误写成长期偏好
- 不确定、否定、推测性表述进入画像

## 6. 当前不建议直接照搬的地方

以下内容暂时不建议直接从 `memory-lancedb-pro` 照搬：

### 6.1 复杂 dedup 决策树

例如：

- `merge`
- `support`
- `contextualize`
- `contradict`
- `supersede`

对 VMM 当前阶段来说过重。

更适合先做一个简化版：

- 摘要：`create / skip / support`
- 画像：`merge / skip`

### 6.2 Preference token 归一细节

例如：

- 英文冠词剥离
- 品牌/单品偏好词归一

这些更适合未来“偏好类结构化提取模块”，而不是现在就塞进 `NoiseGate` 或摘要提炼主链。

### 6.3 直接把短文本统一当噪声

`memory-lancedb-pro` 中的某些短文本过滤成立，是因为它作用在后续候选层。

VMM 当前不能直接沿用为“最终入库判断”，否则会误杀很多中文短偏好。

## 7. 当前最值得优先验证的未决问题

以下问题仍需真实数据验证后才能形成决案：

1. 提炼触发阈值应是多少轮最合适
2. 历史摘要附带多少条最稳
3. 历史摘要带多少字节最合适
4. `summary` 与 `profile` 是否应由一次 LLM 输出同时产出
5. 候选校验器应采用纯规则、向量辅助，还是再加一次轻量 LLM 判定
6. 画像更新是否要区分：
   - `session-level`
   - `user-level`
   - `project-level`

## 8. 当前建议结论（非决案）

基于当前分析，建议先把未来方案理解为三层：

1. 原始轮次稳定入库
2. 达到阈值后异步批量提炼
3. 摘要与画像分流处理

其中最值得从 `memory-lancedb-pro` 借鉴的是：

- 提炼触发门槛
- 提炼前预过滤
- 候选结果再验证
- profile 聚合合并

而不建议现在直接照搬的是：

- 复杂 dedup 状态机
- 偏好 token 归一实现细节
- 将其某一层的长度规则直接硬套到 VMM 当前最终准入门上

因此，这份文档的结论是：

- `memory-lancedb-pro` 的整体分层思路非常值得借鉴
- 但 VMM 需要结合当前“每轮原始入库、后续批量提炼、画像头部注入”的目标做本地化调整
- 现阶段更适合继续做方案收敛与样本验证，而不是直接按单一路径定案
